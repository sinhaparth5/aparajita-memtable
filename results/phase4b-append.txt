Measured on a rented host, not the development laptop, per the rule in CLAUDE.md.

host:     GCP c4-standard-16, us-central1-a
cpu:      Intel Xeon Platinum 8581C @ 2.30GHz (Emerald Rapids), 16 vCPU, AVX-512

gcc:      g++-14 (Ubuntu 14.2.0-4ubuntu2~24.04.1)

The instance was created for this run and deleted immediately after; both it and

== what is being controlled ==
One host, one RocksDB tree, one set of build flags, one uninterrupted session.
The only thing that differs between the two halves of every table below is the
contents of include/aparajita: copy-on-write (the previous commit) against
append-only (this one). Only the plugin object and the two benchmark binaries are
rebuilt between halves.

The skip_list rows are the check on that. They are the same rep in both halves, so
anything that moved them would have moved outside the plugin. They agree to within
0.5% on db_bench and 3% on memtablerep_bench.

Nothing else ran on the machine during the benchmarks.

== arena, standalone structure, 500,000 keys of 16 bytes ==
                        copy-on-write   append-only
   arena per key            445.4 B        100.6 B      -77.4%
   of which key bytes        16.0 B         16.0 B
   of which structure       429.4 B         84.6 B
   live structure           ~40 B          ~40 B        44,378 nodes, 11.3 keys each
   insert                  1189.6 ns       717.2 ns     -39.7%
   lookup                   962.0 ns       770.7 ns     -19.9%

Copy-on-write allocated a whole 384-byte payload per insert. The append-only node
allocates only when a node splits.

The lookup figure is the one worth noticing: the read path was not touched in this
phase. It improved because the live nodes stopped being scattered through ten
times the memory they occupy.

readwrite -- one writer, three readers -- is the one thing that got worse, and it
is the predicted cost rather than a surprise. Copy-on-write had a writer touching
only memory no reader could reach, because the payload it was building was not yet
published. An append writes into the live node, so a reader searching that node
shares a dirty line with the writer filling it.

It reproduces on both hosts at the same magnitude: +14.3% here, +13.5% on the
laptop under WSL2. The structure is still a third faster than the skiplist on that
benchmark, so the trade is recorded rather than paid down. Quantifying it properly
wants HITM counters and belongs to Phase 4.

TSan needs `sysctl vm.mmap_rnd_bits=28` on Ubuntu 24.04, or it aborts at startup
with "unexpected memory mapping" before running anything. That is the kernel's
ASLR entropy, not a fault in the target.

== mutation testing, same host ==
Eleven mutations applied to the new code, each run against all three local test
binaries. The column is which binaries caught it.

caught    order_count off by one nibble                        by: search memtable concurrent
caught    order_slot drops the pad-slot borrow                 by: search memtable concurrent
caught    avx512 permute drops the slot+1 bias                 by: search
caught    avx2 permute forgets the signed bias                 by: search
caught    avx2 permute blends the wrong source half            by: search
SURVIVES  masked load becomes unmasked                        
caught    append reuses an occupied slot                       by: memtable concurrent
caught    prefix-breaking key gets an ordinary lane            by: memtable concurrent
caught    append skips the hint update at rank 0               by: memtable
caught    split keeps the stale prefix                         by: memtable concurrent
caught    fill publishes an identity order off by one          by: memtable concurrent

Three of these are caught by test_search and by nothing else, and that is the
finding worth carrying forward. sorted_position confirms every SIMD candidate
against the comparator and falls back to binary search, so an ordered kernel
returning noise still produces correct lookups, correct iteration and a
byte-for-byte match against RocksDB's skiplist. A permuted kernel is only ever
checked in test_search.

The survivor is deliberate. Unmasking the vector load cannot change a result -- it
is a data race and nothing else -- so no deterministic test can catch it, and
ThreadSanitizer cannot either: GCC instruments the enclosing function but emits
the 64-byte load with no __tsan_read in front of it, confirmed by disassembling
lower_bound_perm_avx512. The mask is justified by the memory model alone.
